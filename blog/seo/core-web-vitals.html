Core Web Vitals Explained

By SP Siam Ahmed · Published 26 November 2026 · Updated 26 November 2026

Core Web Vitals are Google's three measurements of real user experience: how fast the main content appears, how quickly the page responds to input, and how much the layout jumps around while loading. They are ranking signals, but more importantly, they are a fair summary of whether a site feels good to use.

What Are Core Web Vitals?

Unlike lab tests that run on a fast computer, Core Web Vitals come from real visitors on real devices and networks, collected through the Chrome User Experience Report. A page needs enough real traffic to get a score; new or low-traffic pages can use lab tools like PageSpeed Insights to estimate the same metrics.

Google's thresholds for a “Good” experience are: LCP 2.5 seconds or less, INP below 200 milliseconds, and CLS below 0.1. A page should pass all three, for at least 75% of visits.

LCP — Largest Contentful Paint

LCP measures how long it takes for the largest visible element — usually a hero image or a big heading — to render. A slow LCP means the visitor stares at a blank or half-loaded page.

Common causes: a large unoptimised hero image, a slow server, render-blocking CSS or JavaScript, and web fonts that delay text. Fix it by optimising the hero image, loading critical CSS first, and keeping the page's first render light.

INP — Interaction to Next Paint

INP measures responsiveness: when a visitor clicks a button or taps a menu, how long until the page visibly reacts? The target is under 200 milliseconds. INP replaced the older First Input Delay (FID) in 2024, because it measures the whole interaction, not just the first one.

Common causes: long JavaScript tasks that block the main thread, too much JavaScript overall, and event handlers that do heavy work synchronously. Fix it by keeping scripts small, breaking up long tasks, and deferring anything that is not needed for the first paint.

CLS — Cumulative Layout Shift

CLS measures visual stability: how much the page's content moves around while it loads. A score below 0.1 is good. Layout shift is what makes you tap the wrong link because an image loaded above it and pushed everything down — it is the most annoying of the three.

Common causes: images without width and height attributes, web fonts that swap in late, ads or embeds that inject content, and content added above existing content. The fix is mostly discipline: always give images dimensions, reserve space for anything that loads late, and never insert content above what the user is already reading.

How to Measure Them

  • PageSpeed Insights (pagespeed.web.dev) — lab and field data for any public URL, with specific suggestions.
  • Google Search Console — the Core Web Vitals report shows real-user data across your whole site, grouped by URL pattern.
  • Chrome DevTools — the Performance panel and Lighthouse audit measure the same metrics locally while you develop.
  • web.dev — the performance course explains each metric in depth.

How to Improve Each One

For LCP: optimise the hero image (see Image Optimization for Faster Websites), remove render-blocking resources, and use a fast host. For INP: ship less JavaScript, split long tasks, and avoid doing heavy work inside event handlers. For CLS: set image dimensions, reserve space for embeds, and use font-display: swap carefully with a fallback font that matches your web font's size.

Improvements compound: a page that loads fast usually scores well on all three, because the same habits — small assets, minimal JavaScript, reserved space — help every metric at once.

Conclusion

Core Web Vitals are not a game to win; they are a mirror. LCP asks “did the content arrive quickly?”, INP asks “did the page respond?”, CLS asks “did anything jump around?”. Answer yes to all three for most of your visitors, and your site will feel fast — which is what your visitors actually care about, and what Google rewards.
